# Objective First

No work before the aim is written down. Most failed tasks fail at minute zero: the goal was never stated, so nothing could be checked against it. This skill produces the Objective Card and holds every later step accountable to it.

## Core rule: the aim is a sentence, not a topic

"Improve the website" is a topic. "Increase completed contact-form submissions from visitors arriving via the portfolio page, measured over 30 days" is an aim. The aim names the change, the beneficiary, and the measure. If the user cannot fill those three slots yet, that gap is the first task — not a reason to start building.

## The pass

**1. Extract the stated request verbatim.** What was literally asked for.

**2. Ask the aim question.** What is the main aim and objective — what should be different in the world when this is done? One sentence. If the user's request is a solution ("build me a CSV"), recover the problem behind it: what decision or outcome does the CSV serve?

**3. Distinguish aim, objective, and deliverable.**
| Level | Question | Example |
|---|---|---|
| Aim | Why does this matter at all | Get hired in field X this year |
| Objective | What measurable change, by when | 20 tailored applications sent by March 31 |
| Deliverable | What artifact ships | CV v3, cover-letter template, tracker CSV |

A deliverable without an objective above it is flagged: it may be work for work's sake.

**4. Fill the Objective Card.**
- Aim (one sentence, names the change)
- Beneficiary (who feels the difference)
- Success criteria (2–4, each verifiable by a named check)
- Non-goals (what this task deliberately does NOT attempt — the scope fence)
- Hard constraints (budget, deadline, tools, jurisdiction)
- Kill condition (what discovery would make this task not worth continuing)
- First step (15 minutes or less)

**5. Confirm or challenge.** Read the card back. If two success criteria conflict, or the deliverable cannot reach the aim, or the kill condition is already true — say so now, before any work. A contested aim routes to self-debate.

**6. Anchor execution.** The card goes at the top of the task's STATE file (Long_Task_Memory_Protocol.md). Every later step, and every scope-change request, is checked against it: serves the aim → proceed; serves nothing on the card → refuse or renegotiate the card first.

## Anti-patterns

- Filling the card yourself from guesses; the user owns the aim, the skill owns the questions.
- Cards with five aims — one card per aim, or the task is really several tasks.
- Treating the card as ceremony and never re-reading it; step 6 is the point.
- Letting "everything is a priority" pass; force ranking of success criteria.

## References
- Goal-setting research: Locke and Latham — specific, measurable goals outperform vague intentions
- "Working backwards" (Amazon PR/FAQ) — deliverable justified by the customer outcome behind it
- Rumelt, *Good Strategy Bad Strategy* — diagnosis before action; fluff detection
